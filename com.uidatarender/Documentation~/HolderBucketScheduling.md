# Holder bucket scheduling

`HolderBucketScheduler<TState>` is an explicit main-thread update queue for 1–256 ordered holders. The default `Rotating` strategy groups consecutive holders into buckets of at most 128 and refreshes at most one dirty bucket per `Tick(frame)`. Both buckets remain visible every frame. Existing synchronous holder and renderer APIs keep their behavior.

Supply one `IHolderStateApplier<TState>`, a material factory, a texture binder, and a resource-version callback (normally `() => UIPrefabManager.Instance.TextureVersion`). The applier replays the complete snapshot, generates that holder once, and returns its draw position. `BeginBatch`/`EndBatch` bracket a selected bucket; stable UIImage query scopes can be opened here. `EndBatch` must safely close any scopes opened before an exception.

1. `ReplaceMembers(orderedHolders, initialStates, frame)` stages and prewarms both mesh copies for every bucket. Check the returned status before drawing. Cache handles from `GetHandle(index)` after success.
2. `Submit(handle, in state, frame)` copies the latest complete state and returns its version. It does not generate geometry. Repeated submissions coalesce; they do not reset the first pending frame.
3. Call `Tick(frame)` once after submissions. On the ordinary successful path, a request submitted before this call completes this frame or the next. Calls after this cutoff become eligible next frame. Duplicate same-frame ticks perform no extra refresh; backwards frames and reentrant operations are rejected.
4. Use `HolderBucketCameraPass` for a single Built-in HUD camera, and call `Refresh(matrix)` after updates. It records all visible buckets in input order and checks for changed publication/resource versions before camera rendering. Dispose the camera pass before the scheduler.

`TState : struct` is not a deep-copy guarantee. Store values or immutable assets whose lifetime you control, never a mutable shared template or mutable collection. The scheduler exclusively owns generation and positioning of enrolled holders. Width/color/position updates are suitable ordinary snapshots; changed template hierarchy, Canvas/root contracts, Sprite/Text resources or topology require an explicit barrier. Retain external holders and assets until the barrier finishes; a C# reference does not prevent an external `Destroy`.

`FlushAll(reason, frame)` regenerates all latest snapshots into staging renderers and publishes only after every bucket succeeds. Use it for structure/resource changes or explicit recovery. These synchronous barriers are outside the ordinary one-bucket budget and must be reported separately. Successful membership replacement invalidates all old handles; a failed replacement preserves the old membership and output when resources are still valid.

Generation/upload/binding errors leave the visible front unchanged, preserve pending versions and set `Faulted`. No ordinary retry occurs until explicit recovery. A resource-version change sets `NeedsResync` and prevents drawing old bindings. Inspect `LastError`, restore a consistent resource layout, and call `FlushAll`. Initial failure has no output to draw. Caller-owned holders/assets are never disposed by the scheduler.

Each bucket owns two reusable renderers. `GetStorage()` reports allocated renderer/mesh/material counts and Unity-reported mesh/material bytes; this excludes managed queue/scratch buffers and external assets. Query it outside measured updates. `GetPublishedMesh` is inspection-only: never mutate or destroy the returned mesh.

Ordered buckets use contiguous texture batches. A/B/A with one available slot remains three batches. A single holder exceeding slot capacity is rejected. More than one physical mesh per logical bucket is valid; count actual meshes/draws. The supplied camera pass targets an exclusive Built-in HUD pass (`AfterForwardAlpha`); SRP, multiple cameras and ordering interleaved with external transparent objects are outside this contract.

`SingleBucket` and `SameFrame` are synchronous comparison strategies using the same snapshots, publication and camera path. They do not have the ordinary rotating one-bucket work limit. Sample configuration `useBucketScheduling` plus `bucketStrategy` opts into this comparison. Reports include request/completion traces, two explicit drain frames per workload, final geometry hashes, update and draw CPU, initialization cost and owned object storage. The 1.5 ms p95 working target requires matched device measurements; it does not waive the original RC budget or unavailable allocation counters.
