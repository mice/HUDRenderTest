## Context

The current representative fixture has 256 holders, three Sprite images and six primary-atlas TMP glyphs per holder, Slim storage, query reuse and Rotating buckets. Previous Release candidates measured about 8.0 ms generation and 1.15 ms merge per completed Burst bucket. `generationMs` is `updateCpuMs - mergeMs`, including submission and publication. Bucket mode currently rejects detailed diagnostics and reports all inner stages unavailable.

The user explicitly prefers GC acceptance through Unity Profiler to keep production measurement code small. Existing event diagnostics remain compatible, but this change adds no runtime allocation counter or byte-provider abstraction. Android IL2CPP currently disables a potentially crashing allocated-bytes API; that safeguard stays intact.

## Goals / Non-Goals

**Goals:** Attribute rotating generation costs; prove probe on/off output equivalence and report measurement disturbance; capture actual Unity rendering dimensions; use a separate Profiler diagnostic for GC attribution with a positive control and known sample boundaries.

**Non-Goals:** Change generation semantics, cache text geometry, skip TMP reparsing/Canvas updates, change GC acceptance to global zero, satisfy unsupported IL2CPP byte counters by assumption, optimize hot paths, finish stock scene measurements or exact RC validation in this change, publish, change dependencies or budgets.

## Decisions

1. Reuse `BuildMeshDiagnostics` and existing value-type timing aggregates. Default-off per-call timing uses timestamps and numeric fields; no per-character timestamps, per-frame collections or export/log writes in the sampled hot path. Extend rotating collection to observe holders actually completed, avoiding selection-time inference or a separate legacy workload. Keep counts/availability sufficient to reject incomplete or stale records.
2. Add TMP boundaries for Canvas update, forced TMP mesh update, extraction, and final transform. Preserve their existing call order and input handling. Reuse holder/Image stages for setup, data initialization, dispatch and Sprite work. Document inclusive parent/child relationships; report any unclassified remainder rather than summing overlapping stages or subtracting percentile summaries.
3. Compare the same Release APK with diagnostics disabled/enabled in preregistered alternating repeated runs on Mi 10: 256 holders, Sprite3/TMP6, Rotating, Slim/query reuse, 60 FPS, 60 warmup and 3000 samples per mode plus two drain frames. Preserve 2340x1080 landscape and record actual Screen/camera dimensions. Record requests, geometry, source/dependency/resource hashes and environmental endpoints. Probe-off timing remains the normal-path performance evidence; probe-on data identify inclusive costs, not hypothetical uninstrumented phase costs.
4. GC acceptance is a separate Unity Profiler session, preferably target Development Player, with Deep Profiling off, bounded stable captures and a known allocation control outside measured HUD frames. Reuse stock Unity profiling APIs, retain raw capture and parse frame/sample hierarchies to attribute GC.Alloc under the HUD call scope. The installed Editor truncates default imports and dense offline/live views exceed the preserved 3 GiB owned-process limit. Use standard native live `RawFrameDataView` of the controlled Main Thread from each paused bounded window before clearing it; save/hash each binary and live export, explicitly mark `readMode=live-buffer`, `captureSaved=true`, `loadSucceeded=false`, and other threads uninspected. This does not claim successful offline roundtrip or all-thread GC. Split each mode's 362 logical advance steps into twelve 30-step windows plus a final 2-step window, retaining one continuous BeginRun and all 906 report frames across 39 windows, each with an independent byte/callstack control. Controls occupy separate real Unity frames and IO pauses the driver; physical frame gaps/latencies and diagnostic wall times are not performance evidence. Label only steps whose pre-call modeFrame is 60..361 with HUD scope; warmup, mode-transition canonical hash readback and final flush remain outside accepted report frames. An Editor-only capture has an explicit platform limit; unsupported Player bytes remain unavailable. Do not add production code solely for GC counters. Local editor acceptance helpers may be disposable artifacts; any reusable helper belongs in editor/test tooling.
5. Correctness tests cover rotating on/off request and final output identity, completed-holder counts, empty/static frame reset, stage inclusion/availability, TMP changed/empty text and actual rendering metadata. Reuse existing allocation tests; Profiler evidence is the primary new GC acceptance. Run original relevant tests first, then required full original tests and relevant stock validation. Raw evidence stays ignored under `TestResults/GenerationProfile` / `Builds/HudRc/GenerationProfile`.

## Risks / Trade-offs

- Timestamp overhead can dominate small stages → measure probe on/off disturbance using the same APK, retain inclusive counts and avoid glyph-level instrumentation.
- Global Canvas update or TMP regeneration may dominate → report observed stage costs; keep behavior unchanged until a separate optimization proposal.
- Profiler capture overhead and byte-counter limitations → separate GC diagnostic from Release timing; positive-control capture and explicit unsupported flags prevent false zero claims. Native live capture is valid Profiler evidence, while full offline reread remains unverified under the memory cap.
- Interrupted order or device drift → preregister runs, reject invalid dimensions/incomplete reports, preserve rejected data and disclose gaps; device finally restores app/request/settings and reads them back.
- Dirty source and tool changes → freeze source manifests before builds and verify inputs after each build; this is traceable working-tree evidence, not an exact RC.

## Migration Plan

Keep the diagnostic switch disabled in ordinary use and preserve old report fields. Add new metadata/stages with explicit availability. Rollback is reverting this measurement-only change; no asset/dependency migration is required. Existing completed changes retain their histories.

## Tool findings and execution order

SDK and actual runs confirmed that metadata and resolved allocation stacks are exposed by native frame views; default history/import length can hide controls and most frames. Dense full-mode imports and live views hit the retained 3 GiB limit. The Editor-only tool therefore uses Game-area camera callbacks, two startup callbacks before each control, a requested 64-frame buffer (unknown effective native limits are not assumed) and 39 small windows. It keeps exact 906-sample coverage, independent controls in every window and reports live versus imported data honestly. The source of large non-sampled allocation traces includes canonical hash readback: this Mono BinaryWriter.Write(Single) allocates temporary byte arrays. These are mode-transition diagnostic work, not sample-frame HUD allocations; retain outside counts without expanding their stacks into the acceptance dataset. Failed captures/imports remain local evidence.

An Editor startup/exit overlapped an ADB daemon restart during the initial phone group. ADB daemon stderr was incorrectly merged with a setting value; stdout/stderr are now separated and stderr retained, with nonzero exits still rejected. The partial timing group is excluded, and the full eight-run group restarts. Subsequent phone timing and project Editor launch/exit are strictly serial; other users' projects are left untouched.
