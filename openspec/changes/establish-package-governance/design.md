## Context

包版本已从 0.1.0 升至未发布的 0.1.2。最初文档快照有 10 个开放 ID 和 4 条完成索引；性能工作现已更新 Documentation~ 文档并归档 PERF-01，实施必须重新读取实际队列，不能恢复旧状态。

原性能 change 已归档至 openspec/changes/archive/2026-09-27-reassess-public-ugui-extraction-performance。新增场景和 RC 门槛由 validate-hud-rc-performance 承接，不编辑历史归档，也不将其中的完成勾选直接用于新增要求。

新微基准记录 119/119 EditMode 和 0 B warm allocation，但没有代表性 HUD 场景实测。该记录提出的 10 us median / 15 us p95 及 1 ms 场景预算，不自动视为用户已批准的发布例外。2026-09-27 查询本仓库 GitHub origin 的远端 tag 成功且为空；此结果不证明 0.1.0 从未以其他方式发布，发布前须重新核对。

## Goals / Non-Goals

**Goals:** 单一文档目录及包版本来源；逐项 TODO 退出记录；明确性能验收、递增 RC、候选验证和正式晋升条件。

**Non-Goals:** 不治理 bundleVersion，不改写 tag，不伪造验证，不把所有 M3/M4 工作强行绑定本版本。本轮提案更新不实施测试或发布。

## Decisions

### 1. 文档目录

以现有 Documentation~/roadmap.md 和 todo.md 为唯一活动入口。逐段合并根副本的独有内容，保留最新性能证据，修正相对链接后移除根同名文件，不留跳转占位。根 README 可链接文档入口。包 CHANGELOG.md 留在 com.uidatarender 内随包分发，不复制到根。

若没有文档目录，先请用户确认专用路径，再创建目录，不能自动回退到根目录。

### 2. 包版本与候选状态

package.json 是唯一版本权威，不建立 VERSION 镜像。现有 0.1.2 为未发布目标；准备首个候选时写 0.1.2-rc.1，对应 tag v0.1.2-rc.1。后续序号递增，已发布或放弃的序号不得复用，既有 tag 不覆盖、不移动。

每个 RC 有独立 changelog 条目：功能、修复（无则 None）、精确 tag 和验证记录。发布提交由 tag 解析并写入发布后证据，不要求 changelog 在同一提交中包含自身哈希。未发布内容保持 Unreleased，发布日期和状态只按真实证据填写。

### 3. 性能范围

首个 RC 前完成 FillData2/FillData3 微基准、成本分析、正确性、预热后 0 B GC 和代表性 HUD 场景验证。场景记录设备/构建模式、负载、预热、采样、regeneration 主线程耗时、帧时间、GC 和 median/p95。优化前后保持同环境；无实现修改时记录当前路径复测，不虚构改善。

旧 5 us / 30x 保持比较参考。未达参考必须给出实测场景、使用预算、残余风险和重开条件，并取得用户明确例外确认，才能判定发布性能门槛通过。已有 accepted 文案不替代确认。PERF-01 已归档则新建 RC 场景/预算后续 ID 并链接历史，不能复用原 ID。

GPU 3/8 槽、完整场景矩阵、Burst/托管 Job 对比留后续周期；实际改动触及这些路径时补对应验证。M3 仅本轮选入发布项绑定 v0.1.2，其余目标未分配；M5 记录治理与发布周期。

### 4. RC 验证和正式晋升

流程：性能门槛通过 → 固定候选提交、准备 RC 元数据/changelog → 验证并发布 RC tag → 针对精确 RC 验收 → 用户确认 → 正式 v0.1.2。

RC 验收覆盖干净安装/编译、包布局、EditMode、PlayMode、测试治理、UIDataRender 行覆盖率至少 70% 和真实 CI。当前真实 CI 执行渠道为 Jenkins。所有证据绑定精确提交，可复用同提交已有结果；不可假设 tag 推送自动触发验证，实际发布须使用验证相同提交的 Jenkins run，或建立并验证可按精确 ref 执行的入口。

失败后修复并发布 rc.N+1，对新候选重验，不能冒用旧提交结果。阻塞可转交但阻止候选验收和正式晋升。正式版保持已验收 RC 功能代码，仅调整版本和发布记录；检查包布局、版本和晋升差异并关联 RC 证据。若增加功能代码改动，必须回到新 RC。正式 tag 须在用户确认后发布。

### 5. TODO 和治理完成界限

稳定 ID 不复用，但任务可按新证据完成归档。4 条旧无 ID 索引分配明确标记的迁移引用；若已有新 ID 则沿用。节点出入口全量审查实际队列，逐项记录 completed/carried forward/deferred/blocked/obsolete、证据和后续 ID，不按初始数量固定活动状态。

治理文档验收可先完成，实际 RC/正式发布任务继续保留在 M5，直至各自验收；不能把流程定义当成发布成功。

## Risks / Trade-offs

- 文档副本已有分叉 → 合并内容，不整文件覆盖新性能记录。
- 已归档性能项被误当成发布通过 → 新增后续场景及预算确认任务，保留历史证据。
- 历史 0.1.0 没有 tag → 保留原条目和未核实状态，不补造历史发布或 v0.1.1。
- tag 与 CI 触发脱节 → 固定候选提交和 run，tag 存在不等于验证通过。
- 迁移破坏链接 → 同时检查内部相对链接及全仓库入口引用。

## Migration Plan

重读状态和 TODO；合并到 Documentation~；建立 M5 发布队列及性能后续任务；完善 changelog/RC 规则；验证文档、ID、版本、OpenSpec、布局；归档完成治理项并保留发布任务。本轮不实际迁移文档或修改候选元数据，实施阶段执行。

## Open Questions

需求方向已确认。待实施产出的证据包括场景负载/预算、未达参考门槛时的用户例外确认、最终候选提交与同提交 CI run、各次 RC 验收及正式晋升确认。
